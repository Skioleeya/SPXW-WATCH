# project_state — 2026-09-15 / period-wallclock-semantics

## 1. 本会话要答的唯一问题

KAI 裁定（原话）：**"必须基于时间，时间是系统最重要的，21:00 21:03 21:06……时间周期才是第一，
桶无效，必须删除这个错误逻辑"**。

于是问题变成：`web/period.js::aggregate` 现在按**桶序号整除**分组
（`outCols = Math.floor(cols / g)`），这是否违背"按挂钟整点分对齐"？

## 2. 结论：**不违背，两者在本项目数值等价**

不是"两种方案取其一"，是**同一个分组**。两级依据（都可复现）：

**依据一 —— 网格起点被所有周期档位整除。**

```
网格起点 = 20:15:00 = 72900 秒（相对当日 00:00）
72900 % 30   = 0   ⇒ 对齐
72900 % 60   = 0   ⇒ 对齐
72900 % 180  = 0   ⇒ 对齐
72900 % 300  = 0   ⇒ 对齐
72900 % 900  = 0   ⇒ 对齐
```

所以第 c 个组的起点恒落在挂钟整点上：20:15、20:18、20:21 … 21:00、21:03。
**`floor(cols / g)` 与 `floor((t − 20:15) / period秒)` 给出同一个组号。**

**依据二 —— 这是既有代码强校验过的前提，不是巧合。**

- `core/session_grid.py::parse_hm` 只接受 `HH:MM` ⇒ 会话边界必然是整分钟；
- `core/session_grid.py::_make_zone`（第 71-76 行）**强校验**每个区段边界落在桶边界上，
  不满足直接 `raise ValueError`（原文："网格会错位，前端按区段切列就会切错"）；
- 因此"整分钟边界 ∪ 桶宽整除"⇒ 组边界必然是挂钟整点。

**所以"改成按时间分组"在这里是恒等变换，改了不会动一个像素。**
真要打破这条等价性，得先改别的东西（周期档位引入不整除 72900 的值，或会话起点不再是整分钟），
届时该改的是注释而非代码 —— **桶序号的唯一真相在后端 `SessionClock`**，
前端按桶分组才是对的。

## 4. 上一会话遗留缺口：为什么"旧语义漂移"复现不出来

上一会话留了一句"新语义同周期内取值个数恒为 1，但旧语义的漂移未再抓到实例"。本会话动手前
先证伪了它，**结论：缺口出在采样位置，不是缺陷不存在。**

- 旧语义（`ceil`）的末组是把"未走满的当前周期"也输出。要让这一列的值**变化**，
  改变必须落在**矩阵最末桶**上。
- 但最末桶的变化必然伴随 `bucket_index` 推进 —— 那一帧本身就在把网格**向右扩一列**。
  于是漂移只在**边界帧**出现。
- 上一会话按 `gap = 3.0s` 抽间隔帧，而帧间隔是 400ms ⇒ **整个边界帧被跳过**。

本会话改成"连抓相邻帧 + 对每一条行取末列"后实测（`group=6`，60 帧连续）：

```
seq 18200  bi 1461  cols 1462  旧末起 1458  旧末 -0.223  新末起 1452  新末 0.021
seq 18201  bi 1462  cols 1463  旧末起 1458  旧末 -0.223  新末起 1452  新末 0.021   ← 边界帧
```

**根因在 cols 的算术上**：`cols = bi + 1`，`1462 = 6 × 243 + 4` ⇒ 末组**已有 4 个桶**，
且组起 1458 的 4 个桶（1458–1461）**早已走满** ⇒ 该组与"完整组"数值相同 ⇒ 旧语义此刻
**不会**漂移。旧语义真正漂移的时刻是 `cols % g == 1`（末组恰 1 个桶 = 刚跨周期），
而这只在**跨周期的那一帧**出现，窗口 60 帧恰好没覆盖。

> **教训（值得记）**：`cols % g` 才是旧缺陷的触发条件，不是"末组不满"。
> 复现这类缺陷必须对准**边界那一帧**，按时间抽间隔帧是抓不住的。
