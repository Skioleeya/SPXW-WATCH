## 交付 1（镜像）—— 为什么改数据端而不是标签端

两条路都能"对上"：
- **(A) 改 shader 数据映射**（采纳）：去掉 `tr = rows-1-r`，帧行 0 → texture 行 0。
- **(B) 反过来，把 HTML overlay 的标签/现货线倒序**（否掉）。

否掉 (B) 的理由：帧的 `strikes` 是**降序**（速查卡 A：高行权价在上），
而 shader 的天然映射就是"屏幕顶 = texture 行 0"。
(A) 让"帧第 0 行 = 屏幕第 0 行"成为**同一条不变量**，与速查卡 A 一致；
(B) 则要把标签、现货线、帧行序三处一起反过来，等于在显示端绕过数据端的错配 ——
正是上一会话"图例色"缺陷的同一类错误（从显示端打补丁）。

**坑（本质）**：`tr = rows-1-r` 的原注释写的是 "inverse Y"，听起来像在修正坐标系差异，
实际是把行序**反了两次**。教训：坐标轴约定必须写成**可判据的等式**
（"帧第 r 行写在 texture 第 r 行"），不能写成"要反转"这类方向性描述 ——
方向性描述无法判断当前代码是零次还是两次反转。

## 交付 2（假 0 带）—— 上限取值的依据，以及被否掉的两条路

**为什么必须有上限**：前向填充（沿用上一个已知 IV）这个假定**只对短跨度成立**。
跨度一长，输出就从"IV 没变"（真 `ΔIV=0`）漂移成"我们不知道"，
而两者在图上都是同一种亮黄绿 ⇒ 无法区分。留白（`None`）是唯一能表达"不知道"的取值。

**上限为什么是 20 桶（= 10 分钟）**：
`config/serialization.json::heatmap_feed_gap_s = 300.0`（5 分钟）是"多久没数据算断流"的既有阈值
⇒ 5 分钟 = **10 桶**。上限取 **2×**（20 桶）是刻意的余量：
低于 10 桶会把**正常**的心跳级空洞也判成留白（把好数据画成窟窿）；
无限大就是本缺陷。**这两个参数是一对**，改动任何一个都要回头看另一个。

**被否掉的两条路**：
- **(B2) 在 `recover()` 里只取最后一段连续桶**（KAI 上一轮未选）——
  这能彻底消掉 bucket 0 本身，但会让"重启后能不能看到重启前的窗口"变成不可预测，
  影响面比渲染层大。**列为残留，未做。**
- **(B3) 给恢复的桶打 break 标记** —— `_row_values()` 已有 `_breaks | _zone_starts` 机制，
  看起来能一行解决。但 break 只留白**那一桶**，不解决"孤桶之后被一路沿用"；
  真正要约束的是**沿用跨度**，不是起点。⇒ 约束加错了地方，否掉。

**为什么阈值进 config 而不是常量**：项目禁止硬编码（业务常量进配置），
且回归 `case_long_gap_is_blanked` 直接**从 config 读**该值 ——
测试与实现共用同一个来源，避免"测试写死 20、实现改成 30 后测试仍绿"的假通过。

## 交付 3（纵线）—— 为什么是自适应步长

上一会话的守卫是**双侧**判断：某方向格宽 `>= 3.0` 才画该方向边框。
1 分档 630 列 ⇒ 2.40px ⇒ 纵线整条消失。**这不是坏了，是阈值语义过粗**。

**被否掉的选项**：
- **(B1) 把固定阈值从 3.0 降到 1.0** —— 线会出现，但间距只有 2.4px，
  在 MSAA 关闭的情况下等于一片密纹（摩尔纹），比没有线更难看，且掩盖真实格宽。
- **(B2) 在 JS 里算好 stride 再传给 shader** —— `cellPx` 在 shader 里已经算出来了
  （`bw = 1/cellPx` 就在手边），再传一个 stride 就是**同一件事的第二份真相**。
  正解：JS 只传"最小线距"这一个**意图**，stride 由 shader 就地推导。
- **(B3) 把默认周期改成 5 分** —— 逃避问题，且牺牲时间分辨率（产品默认值不该为渲染缺陷让路）。

**为什么单位是物理像素**：`resize()` 把 `u_resolution` 设成 `c.width`/`c.height`，
而 `c.width = CSS px × devicePixelRatio` ⇒ shader 里的一切长度都是**设备像素**。
配置键叫 `cellBorderMinPx` 而不叫 `cellBorderMinCssPx` 是刻意的，但**极易误读**
⇒ 已在 `config.js` 与速查卡 L 写明"把 5 当 CSS px 写 = 高 dpi 屏上实际线距减半"。

**坑（API 语义）**：`u_borderMinPx = 0` 推出 `stride = max(1, ...) = 1` ⇒ **每格都画**，
即退化回旧行为，而**不是**"不画"。想完全不画要传 `mix = 0`（`u_borderMix`）。
两个 uniform 各管一件事（画多密 / 画不画），混淆会在做变异测试时给出错误结论。

## 通用教训（写给下一次）

**"这个方向还画不画"必须是单侧判定 + 显式降级路径**。
上一会话的双侧阈值把"格子太窄"和"要不要画"绑成一个布尔量，
一旦为假就整方向消失，且**不报任何错** —— 这正是本会话交付 3 的成因。
正确形状是：先判能力（能不能画），再算参数（画多密），参数永远有定义域。

- **像素扫描必须以现货线为锚**：先前两次误判（只扫 x<1060 / 把 Skew 蓝线当边界）都源于
  锚点错。正解用 HTML overlay 的现货线（`heatmap.js:209`）定标，

  正常 ~90KB ⇒ 用重试循环等到 > 60KB 再取。
