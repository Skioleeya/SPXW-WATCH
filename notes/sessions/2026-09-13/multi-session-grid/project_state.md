# Project State — multi-session-grid

## 这段改动在做什么

把交易日从"锚在 RTH 开盘（09:30）的单会话"改成**多会话网格**：

```
20:15 ─── GTH ─── 09:25 │ 空档 │ 09:30 ─── RTH ─── 16:00
  桶 0            桶 1579  1580-1589   桶 1590      桶 2369
  └────────── 71100s ÷ 30s = 2370 桶，跨午夜 ──────────┘
```

旧行为锚在 09:30，于是 GTH 时段的 `elapsed_s()` 被钳到 0 —— 隔夜与盘前数据**全部
落进第 0 桶**，GTH 根本无法验证。会话真相只有一处：`config/app.json::sessions`；
`SessionClock` 把它展开成"会话 / 空档"交替的区段表，随帧下发到 `session.zones`。

## 本轮修的四处缺陷（都在"报绿但是假的"这一族里）

### A. `check_session_grid.py` 退出码取反 —— 最严重

```python
return 0 if failures else 1     # 零失败 → 返回 1；有失败 → 返回 0
```

后果是双向的：打印"全部通过"却 `rc=1`（任何信 `rc` 的批量脚本会把它判成红的），
**而有失败时返回 0（静默通过）**。后者才是要命的 —— 这个门禁的全部价值就是
"网格铺不满就报错"，取反之后它恰好在真出错时闭嘴。

证伪（工程外探针，`python -c` 内联、不落文件）：把 `sessions` 打成单会话 RTH 后
调 `main()` → 打印 3 项失败、**`RC=1`**。修好后的失败路径确实返回 1。

### B. `check_period_aggregation.py` 的两组对照从未执行

`_slice_checks` / `_index_checks` 都写好了，`GROUPS` 里也有 `[5]` `[6]` 两行的
标题，但 **`evaluate()` 没把它们串进去**：

```python
return (_option_checks(...) + _bound_checks(...) + _aggregate_checks(...)
        + _clip_checks(...) + _invariant_checks(...))      # ← 少了两组
```

于是七组里有两组**从未运行**，`_report` 收到空列表照样打印标题、`failures` 为 0、
最后打印"全部通过"。这是本轮最"值钱"的发现：它不报错、不告警、不显示为空 ——
**只有把 `GROUPS` 的标题数（7）与实际执行的组数（5）对一遍才会发现**。

接线之后立刻暴露了缺陷 C（`--selftest` 里 "alignSkew 忽略时段映射 → 未被抓住"
变成了"已抓住"）。

### C. `web/period.js::alignSkew` 忽略 `grid.index` —— 唯一的**生产**缺陷

`app.js` 已经算好并传入了 `index`（"基线桶号 → 切后列号"），`period_reference.py`
也早已实现 `ref_align_indexed` 并把它写进了对拍用例 —— 但 `alignSkew` 里仍是
`col = Math.floor(b / g) - drop`，**拿原始桶号直接整除**。

后果：切掉 09:25–09:30 那 10 列空档后，RTH 段的每一个 Skew 点都**左移 10 列**，
两块图的横坐标指向不同时刻。这正是这条链路最怕的静默错位（不报错、只是对不上）。

修法：`pos = b` 起步，`index` 非空则查表（`b >= index.length` 记 stray、
`pos < 0` 静默丢弃），再 `col = pos / g - drop`。

**为什么 `index` 允许为 null**（不是兜底分支）：契约有两条入口 ——
有映射就查表；没有映射表示**序列里的桶号已经是切后位置**（调用方已预映射）。
两者必须给出同一结果，这一点由 `[6]` 组的"时段映射路径 ≡ 预映射路径"钉住，
而"忽略映射必须给出不同结果"是非空转判据。

### D. `tools/skew_reference.py::build()` 调用不存在的 `_config()`

在建改动把加载器拆成了"app 配置"与"序列化配置"两个来源，但只落了 `_app_config()`，
`build()` 里那行 `cfg = _config()` 没跟上 ⇒ `check_skew_alignment` 直接
`NameError` 崩溃（整条回归一个断言都跑不到）。补 `_serial_config()` 读
`config/serialization.json`。

## 被 `[1] 行数` 抓了一次

接线让 `check_period_aggregation.py` 从 398 行涨到 **400 行**，`run.py --check`
的 `[1] 文件长度（上限 400 行）` 立刻报 `[FAIL] 共 400 行，超出上限`。

项目硬约束是**严格小于 400**。处置：把 `_slice_checks` / `_index_checks` 两次调用
并到同一行，回到 399 行。**没有**去放宽上限，也没有把它们塞进别的文件 ——
这条检查抓得对，改的是我的排版。

## 记录层面的教训（承接上一轮）

上一轮的教训是"记录里写了 ≠ 系统里有"。这一轮补两条同族的：
**"检查里写了 ≠ 检查里跑了"**。`_slice_checks` 存在、`GROUPS` 有标题、README 说
"七组对照" —— 三处都写着，但它一次都没执行过。凡"有 N 组对照"这类声明，
判据是**数一遍实际执行了几组**，不是读代码里有没有这个函数。

**"系统里没有" ≠ "系统坏了"**（本轮踩到的误判，KAI 澄清后修正）：上一轮"已设"的
验收定时任务在本会话查不到，我直接定性为工具缺陷并**重建了两次**（第二次是
`cdf2faac-…`）。KAI 澄清：**自动任务"不见了"是他有意为之** —— 他手动在 GTH 时段
验收，不要设自动任务。本会话创建的那个已删除。
⇒ 下"这是缺陷"的结论之前，先问一次"**是不是有人故意这么设的**"。
本项目的记录习惯里"不吹绿"是对的，但"发现异常即定性为缺陷"越界了。

- **把 `alignSkew` 的 `index` 设成必填**（连带改 `skew_reference` 的 node 驱动去
  造一份恒等映射）：被拒。`period_reference.py` 的驱动已经明确用 `index: null`

  `sliceZones` 产出一次。
