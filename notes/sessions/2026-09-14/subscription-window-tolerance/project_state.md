# Project State — subscription-window-tolerance

## 为什么是"配置级"而不是"改跟随逻辑"

KAI 在两条路里选了 A：

- **A（本轮）**：把**订阅**窗口放宽到 ±20，**显示**窗口保持 ±12。容差 8 档 = 40 点。
  代价 = 订阅数 49 → 81（自设上限 92，IBKR 硬上限 100），帧体积不变（帧按**列**增长，
  行数与订阅无关：`FeatureEngine._session_refs()` 给的是已订阅集合，`StrikeWindow.rows()`
  再从里面挑 ±12 ⇒ 显示、Skew、帧大小全部不动）。
- **B（未做）**：`WindowFollower` 改为订阅"**走过路径的显示窗口并集**"，容差 ~105 点。
  能扛单边趋势日，但跟随逻辑从"滑动窗口"变成"累积并集"，需要额外的收缩策略，否则
  订阅数会随时间单调增长到上限。

**A 的天花板是 40 点**：单边趋势超过 40 点时，滚出的档位仍会在显示窗口内留下空洞。
这不是 A 的实现缺陷，是 A 的定义边界 —— 选 A 就等于接受"40 点内往返不掉档"。
`side ≤ 22` 由 `4×side+1 ≤ 92` 决定（IBKR 100 条是更松的那条），所以就算把 A 顶到 22
也只有 50 点，**量级上补不上趋势日**。要覆盖趋势日只能走 B。

## 判据是推出来的，不是拟合出来的

```
S − R ≥ T        S = num_strikes_each_side，R = heatmap_rows_each_side，
                 T = recenter_trigger_strikes
```

推导：重建触发是"中心行权价偏移 ≥ T 档"。两次重建之间中心最多滞后 T 档，故现价可探出
**已订阅窗口** T 档。此时

- 显示窗口最低一档 = 现价 − (T + R − 1) × 步长
- 订阅窗口最低一档 = 中心 − (S − 1) × 步长

要求前者不低于后者 ⇒ `T + R − 1 ≤ S − 1` ⇒ `S − R ≥ T`。

`tools/check_window_tolerance.py` 的 `[3]` 用容差 `T−1`（应出洞，实测 52 个）与 `T`
（应无洞）两条对照把边界钉死 ⇒ 这个 `≥` 是**紧的**，不是随手取的数。

**这条纪律的由来**：同一会话早些时候，我曾提议"重测带宽再重新标定压缩比阈值"，
KAI 驳回 —— 拿观测去拟合阈值就是吹绿。`check_ws_compression` 当天红/绿换身份
（10:3x 报 71.8% < 80%，11:1x 却 RC=0，中间只发生过断线）正是"绝对阈值门禁"的
典型症状。所以这次宁可花力气把下限**推**出来，也不试一个数。

## 排除的选项

- **把 `num_strikes_each_side` 改回 12**：那是回到出洞的配置。回归红了要查夹具，
  不能改被测对象。A/B 已证明红是夹具靶档漂移造成的。
- **放宽测试断言**（例如把"观察行已建立"改成"要么有行要么跳过"）：补丁式绕过。
  真正的缺陷是靶档锚点错了，改断言只会把假红变成永久盲区。
- **把 `display_window_strike()` 做成"自动挑一根在窗口内的档位"**：会静默吞掉配置
  错误。现在越界直接抛错 —— 夹具失效必须响，不能悄悄换一根。
- **改 `tools/selfcheck_config.py` 的 `[4]` 跨文件引用扫描，让它跳过 `_` 开头的注释键**：
  那是在放宽门禁来消掉自己制造的噪声。改的是我写的注释措辞，不是检查器。
- **把"容差 ≥ 触发"只放进行为回归**：静态那条永远跑、代价近零；行为那条慢且重。
  两条都要，理由见 `RULES.md §6.6`。

## 踩到的坑

### 夹具靶档不得锚在阶梯端点

`SyntheticSurface.strike_grid(spot, step, each_side)` 生成 `-each_side … +each_side`
的**对称**阶梯，所以 `grid[3]` = `现价 − (each_side − 3) × 步长` —— 一个**随订阅半径
漂移**的绝对行权价。两个回归都把它当"现价下方第 3 档"（注释里也这么写），订阅半径
一从 12 变 20，它就从 6455 漂到 6415，落到显示窗口之外 ⇒ 断言变成假红，且失败信息
（`观察行已建立 行权价 6415`）看起来像产品坏了。

**同类风险**：任何"从固定索引取一根档位"的夹具都会这样。判据是问"这个下标对应的
语义在配置变化时是否保持不变"。

### 硬编码的测试夹具就是第二份真相

`smoke_test::_status()` 里 `subscribed=74` 与任何真实取值都对不上 ——
它从来没有来源，只是没人核对。已改为从配置派生。
⚠️ **当时写的 `4 × each_side + 1` 也是错的**：正确口径是 `4 × each_side`
（窗口 `below[-side:] + above[:side]` 不含中心档；现货单独订阅、不计入 `count`）。
实测 `订阅 N/92`：±12 → 48、±18 → 72、±20 → 80，全是 4 的整数倍。见 `handoff.md`「订正」。
与 `check_persistence` 手写配置夹具（`RULES.md §6.5`）是同一类问题。

### `cancel_stale_before_add` 与 `_prune()` 的组合才是空洞成因

单看任何一个都不构成缺陷：

- `cancel_stale_before_add` 是**对的** —— 不撤旧订阅，订阅数会在换档瞬间翻倍，直接
  撞 Error 300。
- `HeatmapEngine._prune()` 只按时间裁剪也是**对的** —— 行权价轴该不该存在是 L3 的
  显示窗口决定的，不该由引擎按数据到达情况裁剪（否则会出现"行自己消失"的图）。

两者叠加才产生"该行还在、中间空一截"。**修在订阅窗口的容差上，不要动这两处。**
