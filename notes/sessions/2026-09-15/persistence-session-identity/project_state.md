## 根因：会话身份没进表结构

`bucket_index` 是**日内坐标**（`0..2369`，从会话开盘 20:15 起算），**每个交易日
复用同一段序号**。旧表主键只有 `bucket_index`，于是"这一行属于哪一天"**没有任何
地方记着** —— `recover()` / `recover_skew()` 的 SQL 也没有过滤条件，读全部行。

三条独立后果，**同一个根因**：

1. `serialization/frame_encoder.py:67` 的 `skew.latest` 取 `frame.skew_series[-1]`
   （`SkewEngine.series()` 按桶序号升序）⇒ 昨天 index 2183 的点排在今天 index 527 之后，
   **帧把昨天 14:26:48 报成"最新"**。`ws_probe` 的「25Δ Put 行权价低于现价」因此 FAIL。
2. `skew.series` 混入 871 行昨天的点，label 用**今天的**网格算 ⇒ 出现"今天 14:26"这种
   **尚未发生**的时刻，Skew 面板把曲线画到未来。
3. 热力图按今天的行权价窗口去查昨天的 IV ⇒ 昨天的 RTH 数据被画在**今天 GTH 的时刻**上
   （index 448 → 今日 23:59）。

**顶栏是对的、Skew 面板是错的**：顶栏读 `atm` 块（`skew_point`，每轮现算）；
面板读 `skew_series`。⇒ **只看顶栏看不出来**，这是本条最阴的地方。

同一条根因也解释"20:15 起满宽假 0 带"：bucket 0 的孤桶被 `_row_values()` 前向填充沿用。
`heatmap_max_ffill_buckets`(20) 只是把带宽从 1308 列压到 20 列，**没有消除它** ——
因为**带还在**，只是短了。本轮把旧表丢掉之后，20:15–20:35 那块绿带**一并消失**（截图对照）。

## 方案取舍

**选定：会话身份进表结构（`session_key` = 当日到期日），主键 `(session_key, bucket_index)`。**

会话身份取**当日到期日**而不是"日期字符串"，理由是项目已有唯一口径：
`FeatureEngine._sync_session()` 与 `check_session_rollover.py` 都以到期日为会话身份
（0DTE 的到期日**就是**会话的身份，两个会话必然是两张合约）。用日期会在
"20:15 开盘跨午夜"的网格上产生歧义 —— 一个会话横跨两个自然日。

**被否的方案**：

| 方案 | 否掉的理由 |
|---|---|
| `recover()` 只取"最后一段连续桶" | **依赖"桶序号单调"** —— 只对"跨一次重启"成立。会话早期（今日 index 还是个位数）昨天 index 0..9 的行仍会被当今天用。KAI 上一轮也已否过 |
| `recover()` 按"`bucket_index` ≤ 当前桶号"过滤 | 同上，早期失效；且会**静默**丢掉今天还没写到的桶 |
| 加 `ts` 列（只加给 `heatmap_buckets`） | 能判断归属，但仍要**猜**（今天的 ts 落在昨天 ts 之前？）—— 表结构里本来就有确定信息可用（到期日），不该退化成时间比较 |
| 手工清空 `data/` | 只治当前、明天重演；且是破坏性操作 |
| 保留旧行、加 `session_key` 默认值回填 | 旧行**没有**这个信息，回填只能编 —— 等于把错值固化进库 |

**旧行一律丢弃，不迁移**：它们在新会话里本来就无效，行情重跑会重新写入。
丢弃行数写进 `WARNING` 日志（`legacy_dropped_count`）—— **丢弃必须可数**，
否则就成了比错值更难发现的静默数据丢失。

## 两条配套纪律（防止缺陷换形状回来）

1. **`enqueue()` / `enqueue_skew()` 的 `session_key` 是必填、空值抛错。**
   如果允许 `""`，写入侧就能造出"无身份的行"，缺陷会从"恢复时读错"变成
   "写入时就已经错了"，而后者更难查（表里看不出哪行有问题）。
2. **`_persist_current_bucket()` 只在 `_session_key` 已落定时才写。**
   该值由 `_sync_session()` 在每次 `compute()` **最前面**落定，所以正常情况下必然有值；
   加这道闸门是为了让"没跑过会话同步"这种情况**不写**，而不是写一个空身份。

## 判据为什么写成这样

- `_case_cross_session_isolated` 的两个会话**刻意用完全相同的 `bucket_index`**（10/11）。
  这是缺陷的真实形状 —— 若两个会话用不同 index，用例在"没有过滤"的实现下也能过，
  就成了空转。
- `_case_legacy_table_dropped` 同时断言**丢弃行数被报出**与**第二次 `_ensure_table()`
  幂等**。后者防的是"每次重启都把当天数据也丢掉"这种反向事故。
- 非空转验证（`tmp/probe_mutation_cross_session.py`）：把 `_fetch_session_rows` 换成
  "照旧查全部行"（≡ 修复前形态）⇒ 跨会话用例报
  `今日会话应只有 1 个桶，实际 3`；**同批的迁移用例仍 PASS**（它测的是建表，与过滤无关）
  —— 说明这两条用例测的确实是两件事。
